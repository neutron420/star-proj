ABSTRACT1 
Cloud service providers offer horizontal auto-scaling to prevent 
wasting resources by overprovisioning containers. However, this 
approach struggles to respond immediately to unexpected spikes in 
resource usage and has limitations in optimizing resource 
utilization. Vertical auto-scaling overcomes these limitations. 
Vertical elasticity has become increasingly important in recent 
years to provide instant resource elasticity for stateful and real-time 
critical applications.  Nevertheless, vertical elasticity is not actively 
researched and implemented due to limitations in achieving it. This 
paper proposes Elastic Vertical Memory Management (EVMM) for 
stateful applications in the Kubernetes environment, which is the 
de facto standard in the container orchestration space. We 
compared EVMM to an existing Kubernetes environment without 
vertical elasticity and found that it reduced the total execution time 
of container workflows by up to 35% and memory resource 
utilization on nodes improved by 1.5x.

1 INTRODUCTION 
Container technology has become widely used in cloud 
environments due to its portability and lower overhead compared 
to traditional virtualization technologies [1, 2]. Cloud service 
providers offer predefined, fixed-sized containers to ensure 
adequate performance isolation for users. However, due to this

constraint, cloud users often over-provision containers to avoid 
resource shortages [3]. This practice leads to the underutilization of 
system resources (e.g., CPU, memory) in the cloud [4]. For instance, 
an analysis of jobs executed on one of Google's clusters over the 
course of a month found that the average memory utilization of the 
cluster was only 50% [5, 6]. Since it is challenging for cloud users to 
efficiently configure resources within containers, cloud service 
providers offer container auto-scaling. Auto-scaling allows for 
flexible allocation(scale-up) or reclamation(scale-down) of reso-
urces within a container, providing resource elasticity. Resource 
elasticity can be broadly categorized into two types: horizontal 
elasticity and vertical elasticity. Horizontal elasticity adjusts the 
number of containers handling a job, while vertical elasticity 
adjusts the amount of resources allocated to each container. Cloud 
service providers often use a horizontal auto-scaling approach. 
However, horizontal auto-scaling has a relatively high overhead 
when launching new instances, making it difficult to respond 
immediately to unexpected spikes in resource usage. Additionally, 
it is not suitable for applications that cannot be replicated or 
decomposed into smaller, independent units [7, 8]. Vertical auto-
scaling can be used to address the following limitations. Recently, 
there has been a growing need for research on vertical auto-scaling 
to manage stateful applications, such as scientific workflows and 
machine learning jobs, and to provide instant resource elasticity for 
real-time, critical applications [9, 10]. However, container vertical 
elasticity has not been actively researched [11], and related industry 
solutions are difficult to apply in real-world applications. For 
example, the Vertical Pod Autoscaler (VPA) [12], supported by 
Kubernetes [13], the de facto standard for container orchestration 
that provides unified management and control of containers, 
restarts containers when a scale-up in resources occurs, which 
means that tasks must be reinitiated from the beginning [14]. 
Despite the growing importance of vertical elasticity, it is not 
actively researched and implemented due to the limitations in 
achieving it. Each system has a physical limit on its resources, so it 
is not possible to scale CPU or memory indefinitely [15]. In 
particular, achieving memory resource elasticity is more difficult 
than achieving CPU resource elasticity because CPU resources can 
be shared among processes with some degree of flexibility, while 
memory resources cannot. To overcome the constraints of physical 
memory size, swap memory can be considered. Swap memory 
prevents applications from running out of memory and causing 
OOM(out-of-memory) errors [16]. However, swap memory 
allocates some of the disk space to memory, which reduces the 
performance of the application and system [17]. Furthermore, 
because Kubernetes does not support swap memory by default, 
containers that request memory allocations exceeding the system's 
physical memory will cause an OOM error and be restarted [18]. 
Therefore, managing vertical memory elasticity of applications in a 
Kubernetes environment is a challenging problem.

We propose Elastic Vertical Memory Management (EVMM) for 
stateful applications in Kubernetes environments. To the best of our 
knowledge, there has been little research focusing on memory 
elasticity in Kubernetes environments, particularly when swap 
memory is disabled. We begin by modeling the priority of each task 
and then perform a scale-up on the tasks based on these priorities. 
Next, we pause and checkpoint tasks by limiting the CPU usage of 
those that fail to scale-up. If memory pressure does not improve, 
the paused tasks are terminated in order of decreasing priority. 
Conversely, if memory pressure improves, the stopped tasks 
continue from the checkpoint. When comparing EVMM to a 
Kubernetes environment without vertical elasticity, we found that 
the total execution time of container workflows was reduced by up 
to 35%, and container restarts were reduced by up to 70x compared 
to an environment with excessive memory oversubscription. 
This paper is organized as follows. Section 2 introduces research 
on vertical scaling and memory elasticity relevant to this study. 
Section 3 defines the scope of the problem addressed in the paper. 
In Section 4, we mathematically model metrics such as resources, 
penalties, and rewards for task priorities and the magnitude of 
scaling. Section 5 presents an algorithmic representation and 
description of EVMM. Section 6 details the implementation of 
EVMM. In Section 7, we evaluate the effectiveness of EVMM. 
Finally, Section 8 analyzes the contributions of this work and 
outlines future research directions. 
2 RELATED WORK 
Although not as numerous as horizontal scaling, the following 
container-based vertical scaling or memory elasticity research has 
been proposed. ElasticDocker [19] is the first paper to propose 
container-based vertical scaling, and it uses the MAPE-K principle 
to vertically scale Docker-based containers. If the host machine 
does not have enough resources, it migrates containers to another 
machine in real time based on examined metrics. Comparing 
ElasticDocker to Kubernetes HPA, ElasticDocker achieved a 
runtime reduction of about 37%. RUBAS [20] is a technique for 
dynamically adjusting the allocation of containers running in a 
Kubernetes cluster. If the machine to which the application is 
assigned has enough resources, it scales the container vertically; if 
it runs out of resources, it performs a disruptive container 
migration to another machine. Compared to Kubernetes VPA, 
RUBAS improved CPU and memory utilization in clusters by 10% 
and reduced runtime by 15%. However, these early studies used a 
rather simplistic approach to resource scaling, applying the same 
scaling process per job, and did not account for job prioritization. 
Several approaches have since been proposed that utilize vertical 
scaling. Wang et al. proposed DYVERSE [21], which supports 
dynamic vertical scaling in multi-tenant edge environments. They 
propose dynamic prioritization approach that considers workloads, 
communities, and systems to enable dynamic vertical scaling. 
Buchaca et al. [22] propose a predictive vertical auto-scaling policy 
that uses a time-window multi-layer perceptron (MLP) to predict 
the stages of different types of containers and dynamically resize 
containers accordingly. Choi et al. [23] utilized the vertical elasticity 
feature provided by Docker to dynamically adjust computing 
resources to improve system throughput in big data-based 
applications. Kwan et al. proposed HyScale[7], which utilizes both 
horizontal and vertical scaling of containers in a Docker-based 
environment. However, these works did not pay attention to 
memory elasticity. 
Recent research has explored vertical elasticity in Kubernetes 
environments. Zhao et al. [24] proposed a dynamic CPU allocation 
technique tailored for serverless workloads, while SlackAuto [25] 
introduced a slack-aware CPU vertical scaling mechanism to 
enhance efficiency and performance in serverless applications. 
Similarly, CaaSPER [26] dynamically adjusted CPU resources to 
minimize slack and throttling, ensuring optimal usage. However, 
these studies overlooked memory elasticity and did not address the 
container restart issues of Kubernetes VPA. 
Pufferish [27], on the other hand, focuses on memory elasticity 
and shows how container-based lightweight virtualization opens 
up opportunities to achieve memory elasticity. They implement an 
elastic memory manager that leverages containers to flexibly 
allocate memory for tasks. Pufferish is implemented in Apache 
Yarn and has been shown to prevent OOM errors and improve 
memory utilization. However, pufferish is based on environments 
where swap memory is enabled, making it difficult to apply to 
environments where swap memory is disabled.

3.2 Requirements of Vertical Memory Elasticity 
To effectively achieve vertical memory elasticity, a vertical scaling 
solution meet the following requirements: 
3.2.1 Selecting which containers to scale. The servers (nodes) that 
host containers have limited resources, so if multiple applications 
require container scaling at the same time, not all containers can be 
scaled. Therefore, we need to decide which containers should be 
scaled and manage the scaling process to ensure that the remaining 
containers are not scaled. 
3.2.2 Handling containers due to memory pressure. Due to the size 
limitations of a node's memory, some tasks must be stopped when 
their memory requirements exceed the available physical memory. 
However, since stopped tasks generally need to be reinitiated from 
the beginning, a method to avoid this necessity should be devised.

3.2.3 Scaling size of memory. Implementing a fixed-size memory 
elasticity that does not consider the resource usage trends of tasks 
may result in unnecessary triggering of the scale-up mechanism 
multiple times. Therefore, a mechanism should be included to 
dynamically determine the memory scale size based on per-task 
resource usage and usage trends. 
4 DEFINE TASK PRIORITY AND SCALE SIZE 
Vertical elasticity cannot infinitely allocate memory to all running 
tasks due to limitations in host server capacity. We model the 
priority of each task and scale the resources of tasks in order of 
priority. The size of the resource scaling is determined dynamically 
based on the memory usage and allocation trend of the task.

6 IMPLEMENTATION  
The implementation of EVMM requires the ability to monitor and 
control the resources of containers running on each node. For this 
reason, we implemented a module to control the resources of 
containers via the Container Runtime Interface (CRI) API [29]. The 
CRI API is an internal API used by Kubernetes to communicate 
with the container runtime. Additionally, to implement such a 
management module, Kubernetes must be able to dynamically 
change the memory size of a container and support container 
checkpointing. Starting with Kubernetes v1.25 and later, an in-place 
resource resize API has been implemented in the CRI API, and the 
CRI-O [30] runtime environment has started supporting Linux's 
Checkpoint/Restore In Userspace (CRIU) [31] checkpointing feature 
in alpha. We chose CRI-O as our container runtime because it is the 
only runtime that integrates checkpointing into Kubernetes. The 
Kubernetes and CRI-O we used is v1.27, which supports both in-
place resource resize and container checkpoints. 
EVMM is implemented in the Go programming language. The 
program runs on each worker node and manages container 
memory on those nodes. Although the algorithm described in 
Section 5 processes containers sequentially for checkpointing and 
repair, these operations can be time-consuming (as mentioned in 
Section 7). If the program were to wait for each checkpointing and 
repair operation to complete before managing other containers, it 
would be unable to handle additional container management tasks 
during that time. Therefore, the actual implementation utilizes Go 
routines 
to 
handle 
checkpointing 
and 
repair 
operations 
asynchronously in separate threads. Additionally, it is designed to 
manage multiple containers simultaneously, handling requests for 
scale-up/scale-down, pause/continue operations in parallel, enab-
ling immediate responses to resource allocation and repair requests.

Figures 5 and 6 illustrate the normalized average execution time 
and wait time per container for all test workloads. Container 
execution time is defined as the sum of the time the container ran 
and the CrashLoopBackOff time, with the exclusion of the time the 
container was stopped by EVMM. The wait time represents the 
period during which the container was awaiting execution, 
inclusive of the interval during which EVMM terminated the 
container. The time a container is paused is considered part of the 
running time and is therefore included in the container execution 
time. The baseline for normalization is a standard Kubernetes 
environment without oversubscription. Figures 7 and 8 illustrate 
the cumulative distribution functions (CDFs) for container 
execution time and wait time for select workloads. Normalization 
was based on the largest value observed for each workload. 
In Figure 5, EVMM demonstrates good execution times, though it 
is somewhat slower compared to the scenario with the optimal total 
execution time. This is also reflected in Figure 7, where we see that 
in the barnes, some containers experience delays due to pausing. 
Conversely, the radix shows a greater number of containers with 
extended execution times than barnes, which is attributed to the 
high restart rate of containers, leading to a higher proportion of 
containers running for longer durations. Figure 6 indicates that the 
wait time is similar to or slightly higher than in the optimal total 
execution time scenario. This is because EVMM stops the container, 
a new container is allocated, but the wait time reduction is 
amortized because the removed container must also wait to be 
repaired. Notably, barnes has the longest wait time. Since barnes is 
not memory elastic, containers removed by EVMM must wait for 
other containers to complete their work (as shown in Figure 8).  
This increases the wait time, but the total execution time is the 
fastest for EVMM, which is due to the effectiveness of checkpoints.

Table 4 shows the average time taken for checkpoints and image 
creation across all workloads. Interestingly, there is no correlation 
between checkpoint size and duration. Radix had relatively short 
times, averaging 19 seconds, despite having checkpoints more than 
twice the size of those in other workloads. This is likely due to the 
greater impact of container runtime load on each node. For example, 
in raytrace, which has a relatively large number of segments with 
memory utilization higher than ThrContainerStop (as shown in Figure 
4), the shortest checkpoint time was 7 seconds, while the longest 
was 68 seconds, a difference of about 10x. In contrast, radix showed 
less variation, with checkpoint times ranging from 6 to 30 seconds. 
Another factor is the sheer number of containers managed by the 
container runtime. Blackscholes and raytrace have relatively small 
unit container sizes, meaning many containers run on a single node. 
As a result, the container runtime must process scale-up operations, 
checkpoint requests, and other tasks from a large number of 
containers simultaneously, which can slow down processing and 
cause delays. This suggests that we should carefully determine 
when and how often to perform checkpoints. Additionally, 
converting checkpoint data into a container image can also cause 
significant delays: the fastest image creation time for raytrace was 
13 seconds, while the slowest took 190 seconds. We observed that 
delays in checkpointing and image generation were generally 
worse under high-memory conditions and when these commands 
were executed in parallel, which some controls failed to handle. 
8 CONCLUSION 
We propose a new elastic memory management method, EVMM, 
for Kubernetes environments. To the best of our knowledge, no 
previous work has defined and addressed the problem of memory 
elasticity in a Kubernetes environment with swap memory disabled. 
EVMM dynamically scales the resource size of containers up and 
down while monitoring the memory utilization of nodes. It also 
pauses and stops tasks based on priority when memory pressure 
occurs on a node. This minimizes container restarts while ensuring 
memory availability for high-priority jobs. When comparing 
EVMM to a traditional Kubernetes environment without vertical 
elasticity, we found that the total execution time of container 
workflows was reduced by up to 35%, and memory utilization on 
nodes improved by 1.5x. This approach provides an opportunity for 
achieving memory vertical elasticity in stateful applications.  
However, we identified some issues: repairing removed 
containers can cause resource imbalance between nodes, resulting 
in container skewing to certain nodes; checkpointing when a node 
is low on memory can overload the container runtime, causing 
some controls to fail; and restarting tasks with highly volatile 
memory cannot always be prevented by limiting CPU usage. Future 
work will address these issues, further refine EVMM, and integrate 
its capabilities into the Kubernetes VPA.
