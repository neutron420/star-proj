Abstract
Stateful cloud-native services such as databases, queues, and cache-intensive middle tiers
remain difficult to autoscale safely because memory is a hard resource in Kubernetes:
under-allocation creates Out-of-Memory (OOM) failures, whereas over-allocation inflates
cluster cost and reduces packing efficiency. Standard Vertical Pod Autoscaler (VPA)
improves long-horizon right-sizing, but it is primarily recommendation oriented, reactive,
and historically tied to disruptive actuation semantics. The Elastic Vertical Memory
Management (EVMM) approach of Kang and Yu introduced a proactive memory-centric
control loop for Kubernetes-based stateful applications, yet its behavior still depends
on uniform trend logic and fixed thresholds that react slowly to abrupt phase changes.
This report presents Cognitive Elastic Vertical Memory Management (Cognitive-
EVMM), an improved control framework that augments EVMM with workload-state
classification, hybrid forecasting, adaptive thresholds, confidence-aware fallback, and
priority-based memory allocation under node pressure.
The proposed system monitors high-frequency memory telemetry from Prometheus,
models short-term demand using a hybrid Exponential Moving Average and linear-trend
predictor, classifies each control interval as steady, trending, or volatile, and then selects
a state-specific scaling policy. A cognitive decision engine combines usage ratio, rate of
change, forecast confidence, and memory priority to produce an actuation score for in-
place vertical resizing. The design explicitly targets restart avoidance for stateful services
and introduces an OOM-guard panic path for near-limit or high-velocity memory bursts.
Experimental analysis using the project implementation, synthetic and injected spikes, and
comparative plots shows that Cognitive-EVMM reduces spike response latency from 240 s
for standard VPA and 72 s for base EVMM to 12 s, improves resource-efficiency score from
62% to 84% over the EVMM baseline, and achieves approximately 35% lower memory
waste than the base paper under mixed workloads. The controller also shifts OOM safety
margins away from the danger zone while preserving tighter average slack than conventional
VPA, yielding a stronger cost-performance-reliability balance for Kubernetes-based stateful
applications.
Keywords: Kubernetes; Vertical Pod Autoscaler; EVMM; Stateful Workloads; In-place
Pod Resize; Predictive Scaling; Cognitive Control; Memory Elasticity.

Cognitive-EVMM for Kubernetes Stateful Applications
1.
Introduction
1.1. Background: Memory Elasticity in Cloud-Native Platforms
Kubernetes has become the dominant orchestration substrate for microservices because
it unifies deployment, service discovery, fault recovery, and scale control in a declarative
control plane. Most production clusters already rely on Horizontal Pod Autoscaler (HPA)
for throughput scaling and cluster-level autoscalers for node elasticity. However, memory-
heavy stateful services do not benefit from horizontal scaling as directly as stateless request
handlers. Replicating a front-end worker can absorb traffic; replicating a stateful database
replica or stream-processing shard often requires data movement, consistency coordination,
cache rewarming, and storage-aware placement. Consequently, many real-world workloads
remain bottlenecked by vertical resource adequacy rather than pod-count elasticity.
For memory in particular, the operational stakes are high.
CPU overuse usually
leads to throttling; memory overuse leads to kernel reclamation, cgroup pressure, latency
amplification, and eventually OOM termination. These effects are especially harmful for
stateful workloads whose working sets are expensive to reconstruct. A vertical memory
controller must therefore satisfy two objectives that are naturally in tension: it must
maintain sufficient headroom to protect the working set, yet it must avoid persistent slack
that wastes node memory and reduces bin-packing density.
1.2. Horizontal Scaling versus Vertical Scaling
The distinction between horizontal and vertical autoscaling is central to the motivation of
this work.
• Horizontal scaling increases or decreases the number of pod replicas. It is ef-
fective for embarrassingly parallel request processing, but it is less suitable for
monolithic state shards, primary databases, in-memory caches, and single-threaded
state coordinators.
• Vertical scaling changes per-pod CPU and memory allocations. It is the natural
strategy when the application cannot be split quickly, when state transfer is expensive,
or when a single pod must preserve session affinity and warm memory state.
In practice, stateful services often require both. Yet when memory demand rises
abruptly, vertical scaling is usually the first line of defense because it can increase the
survivability of the running process without re-partitioning the application. The challenge
is that vertical scaling has historically been slower and more disruptive than horizontal
scaling in Kubernetes, especially when resource updates require pod eviction or recreation.
1.3. Limitations of Standard VPA
The upstream Kubernetes Vertical Pod Autoscaler improves rightsizing by recommending
or applying CPU and memory request changes based on observed historical usage [2]. Its
design is valuable for long-horizon efficiency improvement, but several limitations remain
critical for stateful memory management:

1) Reactive behavior. VPA is oriented around accumulated observation windows
and recommender outputs, not short-horizon burst anticipation.
2) Weak workload awareness. The same general policy is applied regardless of
whether the workload is stable, trending, or highly volatile.
3) Operational disruption. Although modern Kubernetes now supports in-place
resize capabilities [3,4], restart-free behavior is not universally guaranteed for every
resize case, and conventional VPA workflows historically depended on pod eviction
or recreation.
4) No memory-priority arbitration. VPA does not reason explicitly about which
pods should receive scarce memory first under node pressure.
These characteristics make standard VPA useful for baseline rightsizing, but insufficient
for aggressive stateful memory elasticity where burst survivability and sub-minute response
are required.
1.4. Motivation for Cognitive EVMM
The EVMM baseline by Kang and Yu addressed an important gap by treating vertical
memory scaling as a proactive control problem for stateful Kubernetes applications [1].
It introduced elastic scaling logic that follows observed demand more closely than static
VPA policies and explicitly targets stateful behavior. However, the baseline still exhibits
two structural limitations in bursty environments. First, a single predictive regime is
applied to all workload phases, even though steady nightly traffic, monotonic ramp-up, and
instantaneous spikes require different controller gains. Second, fixed decision thresholds
create either lag or oscillation when cluster conditions and workload volatility change
simultaneously.
The core motivation of Cognitive-EVMM is therefore to make the control loop context
aware. Instead of asking only “How much memory was recently consumed?”, the proposed
system also asks:
• Is the workload currently steady, trending, or volatile?
• How confident is the short-term forecast?
• How much node pressure exists, and which pod should receive memory first?
• Should the controller optimize primarily for efficiency, anticipation, or safety in the
current interval?
1.5. Research Problem and Objectives
This report addresses the following research problem:
How can Kubernetes-based stateful applications be vertically memory-scaled in
a proactive, low-waste, restart-avoiding, and OOM-safe manner under mixed
workload dynamics?
To answer this problem, the report pursues four objectives:
1) design a cognitive extension of EVMM that detects workload phase changes in real
time;

1.6. Key Contributions
The main contributions of this report are summarized below.
• Cognitive control extension. A state-aware controller is proposed to distin-
guish steady, trending, and volatile workload phases and to change scaling weights
accordingly.
• Hybrid prediction model. The work combines exponential smoothing with short-
term trend inference so that the controller remains stable during smooth periods
and still reacts early during ramp-up.
• Adaptive thresholding. Scale-up and scale-down thresholds are adjusted online
using variance, forecast confidence, and node pressure rather than remaining fixed.

arbitrate memory allocation under contention using memory intensity, CPU support,

Related Work
2.1. Kubernetes Vertical Pod Autoscaler
The Kubernetes autoscaling ecosystem includes HPA, Cluster Autoscaler, and VPA. VPA
focuses on right-sizing pod CPU and memory requests over time and is implemented
through recommender, updater, and admission components in the Kubernetes autoscaler
project [2]. Its principal strength lies in improving chronic over- or under-requesting.
However, VPA does not fundamentally solve the control-theoretic problem of short-horizon
memory surges in stateful services. From a research perspective, VPA is a valuable systems
baseline rather than a complete solution for rapid vertical memory elasticity.
2.2. ElasticDocker
ElasticDocker pioneered autonomic vertical elasticity for containerized applications by
adjusting CPU and memory allocations online based on threshold crossings [5].
Its
contributions were important because they demonstrated that containers can be vertically
adjusted with less disruption than virtual machine era scaling methods. Nonetheless,
ElasticDocker predates contemporary Kubernetes-native in-place resize capabilities, does
not focus specifically on stateful microservices in Kubernetes, and relies primarily on
threshold-triggered behavior rather than adaptive cognitive control.
2.3. RUBAS and Non-Disruptive Vertical Autoscaling
Rattihalli et al. investigated non-disruptive vertical autoscaling and resource estimation in
Kubernetes [6]. Their work is valuable because it highlighted the feasibility of modifying
resource allocations without always recreating the pod and quantified estimation challenges
in real clusters. In that sense, it forms an important bridge between static rightsizing and
truly dynamic vertical control. Yet its emphasis is on feasibility and estimation rather
than on memory-specific cognitive decision-making, state classification, or cost-reliability
tradeoff optimization.
2.4. HyScale and Hybrid Autoscaling
HyScale combined horizontal scaling, vertical scaling, and network-level reasoning for
Dockerized microservices in cloud data centers [7]. The paper demonstrated that purely
horizontal or purely vertical scaling is often suboptimal when service chains and network
bottlenecks are involved. This insight remains relevant here: stateful systems also require
coordinated reasoning across multiple resource dimensions. However, HyScale primarily
targets service-level scaling orchestration rather than fine-grained memory control for a
single stateful pod’s working set.
2.5. EVMM Baseline by Kang and Yu
The closest antecedent to this work is EVMM, which targets elastic vertical memory
management for container-based stateful applications in Kubernetes [1]. EVMM recognizes

that memory is both performance critical and failure sensitive in stateful services. Its
baseline contribution is to move beyond static VPA-style resizing and to use shorter
telemetry intervals together with proactive logic for memory adjustment.
The base
implementation in this project captures that philosophy through a memory-priority score,
trend-aware scale-up logic, and reclaim policy under low utilization.
Despite its relevance, the baseline reveals several limitations under mixed dynamics:
• the same general scaling logic is reused across smooth ramps and abrupt spikes;
• decision thresholds are largely fixed;
• prediction confidence is not explicitly used to attenuate risky forecasts;
• emergency handling remains less sensitive to sudden rate-of-change surges than
desired for strict OOM protection.
2.6. Research Gaps
The literature synthesis reveals four research gaps that motivate Cognitive-EVMM.
1) Phase-unaware decision loops. Existing methods usually treat recent telemetry
as a homogeneous signal and do not separate stable, trending, and volatile workload
phases.
2) Insufficient memory-specific urgency modeling.
Many systems optimize
generic resource usage but do not explicitly prioritize memory survivability for
stateful pods.
3) Weak coupling between prediction and confidence. Forecasts are often used
directly even when their statistical reliability is poor.
4) Limited contention-aware allocation. Cluster-level pressure is often ignored
during per-pod vertical decision-making.

3.
System Architecture
3.1. Architectural Overview
Cognitive-EVMM is organized as a closed-loop control pipeline deployed alongside Ku-
bernetes workloads. The architecture follows the monitor-analyze-decide-act pattern but
introduces a cognitive layer between prediction and actuation. The full pipeline consists
of four core modules:
1) Monitoring module
2) Prediction engine
3) Cognitive decision engine
4) Scaling controller
At a high level, Prometheus collects memory telemetry from the target pod, the
monitoring module maintains a bounded history window, the prediction engine estimates
near-future demand, the cognitive engine classifies workload state and computes a scaling
score, and the controller applies an in-place resource patch subject to safety constraints
and cooldown rules.
3.2. Monitoring Module
The implementation queries container_memory_working_set_bytes from Prometheus
every 10 s, converts the metric to MiB, and appends it to a rolling history. The history
length in the implementation is capped at 60 samples, which corresponds to approximately
10 minutes of recent context. In addition to raw memory usage, the controller derives:
• utilization ratio ui(t) = Ui(t)/Li(t),
• instantaneous rate of change ri(t),
• short-window variance and volatility indicators,
• current memory limit from the Kubernetes deployment spec.
The monitoring module therefore serves two roles: it produces operational telemetry
for scaling decisions, and it exposes research metrics such as current score, workload class,
forecast confidence, savings in MB-hours, and panic count via Prometheus-compatible
gauges.
3.3. Prediction Engine
The prediction engine estimates near-future memory demand over a short horizon H. The
implementation uses a hybrid approach:
1) an Exponential Moving Average (EMA) captures short-term smoothed behavior and
filters high-frequency noise;
2) a linear regression model over the recent history estimates the trend slope and R2
confidence;
3) both signals are combined to form a hybrid demand forecast.
This design is intentionally lightweight. It avoids the runtime overhead and training
requirements of heavy machine learning models while still encoding two important intu-

itions: recent usage should matter more than older usage, and persistent ramps should
influence proactive limit changes before threshold breach occurs.
3.4. Cognitive Decision Engine
The cognitive engine is the central innovation of the proposed architecture. It first classifies
the workload into one of three behavioral states:
• Steady: low variance, weak directional trend, low rate fluctuation.
• Trending: strong linear direction with sufficiently high forecast confidence.
• Volatile: bursty or rapidly changing usage with high rate variance or danger-zone
urgency.
After classification, the engine selects a weighting vector for decision features. In steady
mode, direct utilization dominates because efficiency is the primary objective. In trending
mode, forecasted demand receives larger weight to anticipate continued ramp-up. In
volatile mode, rate-of-change and safety take precedence so that the controller reacts
before OOM conditions develop.
The implementation also includes confidence-aware fallback: when forecast confidence
falls, trend weight is attenuated and direct usage receives more weight. This prevents
unstable actuation when linear fit quality deteriorates during abrupt behavioral transitions.
3.5. Scaling Controller
The scaling controller is the actuation layer that patches Kubernetes resource limits and
requests. In the prototype, the controller updates the target deployment through the
Kubernetes API and respects four guardrails:
1) minimum and maximum memory bounds (128 MiB to 4096 MiB);
2) cooldown control (90 s) to limit oscillation;
3) panic scaling when near-limit danger is detected;
4) conservative scale-down to avoid repeated shrinking and re-expanding.
The sample workload manifest explicitly enables memory resizePolicy with restartPolicy:
NotRequired, making the configuration compatible with restart-avoiding vertical adjust-
ments where supported by the cluster version and runtime implementation. In production
terms, this is critical: upward resizing is prioritized because it directly protects the process
working set, while downscaling is intentionally more conservative because some memory
decrease cases may still be operationally constrained even with modern in-place resize
support.
3.6. End-to-End Workflow
The end-to-end workflow for one control interval is summarized below.
1) Prometheus samples the target pod every 10 s.
2) The monitoring module fetches memory usage and updates the history window.
3) The predictor computes EMA, trend slope, and forecast confidence.
4) The classifier labels the interval as steady, trending, or volatile.

4.9. Why the Method Improves on VPA and EVMM
The methodology improves on standard VPA because it is phase aware, short-horizon
predictive, and memory-priority conscious. It improves on the base EVMM design because
it couples prediction with confidence, couples scale thresholds with current variance and
node pressure, and separates controller behavior across workload phases instead of using a
single trend-centric regime. Conceptually, Cognitive-EVMM is not just “more aggressive
EVMM”; it is a different control strategy in which the controller first decides what kind of
memory dynamics it is observing and then chooses the appropriate scaling law.

Experimental Setup
5.1. Cluster Environment
The experimental prototype is implemented as a Kubernetes-deployed Python autoscaler
using the official Kubernetes Python client, Prometheus API client, Pandas-based feature
processing, and scikit-learn linear regression. The autoscaler is packaged as a deployment
with RBAC permissions to read and patch deployments in the cluster. The target workload
is a sample stateful-like containerized application deployed with explicit memory requests
and limits, and with memory resize policy configured to avoid restarts where supported by
the cluster runtime.
The experimental environment includes the following practical components:
• Kubernetes deployment for the autoscaler controller;
• Prometheus for metric collection;
• sample workload deployment with resizable memory limits;
• Grafana dashboards and exported controller metrics for observation;
• workload generators for steady, trending, and burst phases.
5.2. Target Workloads
Two workload-generation paths are used in the project artifacts.
1) Synthetic trace generation. The plot generator combines sinusoidal baseline
demand, random noise, a large sudden spike, and a sustained upward trend. This
produces a mixed workload containing all three controller states in a single experi-
ment.
2) Live spike injection. The spike trigger script allocates a large memory object
inside the sample application pod and holds it for a fixed period, creating a sharp
burst suitable for latency and OOM-guard evaluation.
The mixed traces are intentionally useful for research because they expose three distinct
14
Cognitive-EVMM for Kubernetes Stateful Applications
controller stress cases:
• steady periods test whether the controller can reclaim slack instead of holding
conservative limits;
• trend periods test whether predictive scaling can widen headroom before threshold
breach;
• burst periods test whether the safety logic acts quickly enough to avoid OOM.
5.3. Compared Baselines
Three systems are compared throughout the report.
1) Standard VPA. A reactive baseline with relatively delayed response and historically
disruptive actuation semantics.
2) Base EVMM. The implementation derived from the 2025 EVMM paper, using
priority scoring and predictive adjustment without cognitive phase switching.
3) Proposed Cognitive-EVMM. The improved controller with hybrid prediction,
adaptive thresholds, workload classification, and OOM-guard logic.
The comparison is therefore deliberately incremental: VPA provides the common
Kubernetes baseline, EVMM provides the relevant state-of-the-art research baseline, and
Cognitive-EVMM isolates the gains produced by the proposed extensions.

The experimental design assumes that Prometheus telemetry reflects application memory

actuation quality. They do not attempt to model every possible storage engine or scheduler
implementation detail.

6.6. Response Latency Comparison
Figures 6 and 7 present the most operationally decisive result: burst response latency.
Standard VPA requires approximately 240 s to react adequately to the sudden spike.
For stateless replicas, such latency may be tolerable if horizontal scaling or retries absorb
the disturbance. For a stateful memory-bound container, it is far too slow. The pod can
exhaust its memory working set long before the control plane completes its reaction path.
Base EVMM reduces latency to roughly 72 s by using predictive elastic logic. This is a
major step forward, and it validates the EVMM thesis that memory scaling must move
beyond coarse historical recommendation windows. Yet 72 s is still a long interval for a
steep burst. In a real production system, a sustained queue buildup or compaction event
can reach the OOM boundary well inside that time.
Cognitive-EVMM reduces the latency further to about 12 s, corresponding to a 6×
improvement over base EVMM and a 20× improvement over standard VPA. This is the
strongest evidence that the cognitive layer matters. The reduction does not come from
simply increasing scale aggressiveness globally. If that were the case, waste would explode.
Instead, the system reacts quickly when the workload is volatile and remains conservative
when the workload is steady. The low latency is therefore a result of state-sensitive
prioritization, not brute-force over-allocation.

Discussion
7.1. Strengths of the Proposed System
The strongest property of Cognitive-EVMM is that it improves the multi-objective balance
of vertical memory control. Stateful applications care about continuity, not only average
utilization. The proposed system acknowledges this by elevating restart avoidance and
lower-tail memory safety to first-class design goals. At the same time, it does not abandon
efficiency; it simply stops treating every interval as if it were equally dangerous.
Three strengths stand out.
1) Fast safety response. The controller reacts to high-risk intervals before a hard
limit breach occurs.
2) Efficient calm-period behavior. Resource reclamation is more decisive during
steady phases, reducing cluster-wide memory waste.
3) Explainable logic. The cognitive layer uses interpretable features such as variance,
ROC, confidence, and node pressure. This is operationally attractive because SRE
teams can reason about why a scaling decision occurred.
7.2. Trade-offs and Operational Considerations
No autoscaler is free of trade-offs. The proposed method makes several explicit design
choices.
First, panic scaling intentionally over-allocates memory for short periods to avoid
catastrophic under-allocation. This can temporarily increase slack. However, the evaluation
indicates that the total waste remains lower than that of both baselines because the
controller returns to tight operation quickly after the event.
Second, adaptive thresholds and state classification require frequent, reliable telemetry.
If metric freshness degrades, the controller may act on stale observations. This risk
is mitigated partly by confidence-aware fallback, but robust observability remains a
prerequisite for deployment.
Third, downscaling is intentionally conservative. This is not a weakness but a deliberate
safety decision. In-place upward resizing is usually the highest-value action for stateful
processes; aggressive downward resizing can reintroduce the very instability the system is
designed to avoid.
7.3. Real-World Applicability
The proposed system is especially relevant for the following categories of workloads:
• primary or leader replicas of databases;
• message brokers and queue consumers with bursty memory buffering;
• stream processors with state stores;
• in-memory caches and session services;
• batch and analytics jobs with phase-changing memory footprints.
In such systems, avoiding a restart is often more valuable than preserving a perfectly

minimal memory reservation at every moment. Cognitive-EVMM supports this operational
reality by scaling vertically in a way that preserves service continuity whenever the
underlying platform permits in-place updates.
7.4. Validity Considerations
Several validity considerations should be stated explicitly.
• Workload representativeness. The project uses synthetic mixed traces and
injected spikes, which are appropriate for controller stress testing but do not capture
every application-specific memory pathology.
• Platform semantics. In-place resizing behavior depends on Kubernetes version,
runtime support, and resize direction. The report therefore frames the system as
restart-avoidance oriented rather than making an unconditional no-restart guarantee
for every resize case.
• Prototype scope. The current implementation targets one deployment at a time.
The priority formulation is nevertheless useful because it defines how the same logic
should extend to multi-pod memory contention.
These caveats do not weaken the main contribution. Instead, they clarify the precise
scope in which the presented results should be interpreted: as a robust comparative study
of a cognitive improvement to EVMM for Kubernetes-based stateful memory management.
7.5. Implications for Kubernetes Resource Management
The broader implication of this work is that vertical memory management in Kubernetes
should not be viewed as a narrow recommendation problem. It is a control problem with
workload semantics, uncertainty, and failure asymmetry. Memory under-allocation is far
more dangerous than memory over-allocation for stateful applications, yet indiscriminate
safety margins are economically unsustainable. The results indicate that the right solution
is not a single universal threshold or a heavier forecasting model in isolation, but a
controller that adapts its own reasoning mode to the current operating regime.
8.
Conclusion
This report presented Cognitive-EVMM, an improved vertical memory management
framework for Kubernetes-based stateful applications. The work began from a practical
gap in cloud-native autoscaling: standard VPA is useful for long-horizon rightsizing but
reacts too slowly and too generically for burst-prone stateful workloads, while the 2025
EVMM baseline, though substantially better, still applies a largely uniform predictive
logic across heterogeneous workload phases.
The proposed system addresses this gap through five tightly coupled design elements:
high-frequency monitoring, hybrid short-horizon forecasting, cognitive workload classifica-
tion, adaptive thresholding, and priority-based memory allocation. The resulting controller
shifts policy emphasis according to observed workload state, using efficiency-biased be-
28

havior during steady periods, prediction-biased behavior during trending periods, and
safety-biased behavior during volatile periods. This is the central technical contribution of
the report.
The comparative evaluation shows that the proposed design materially improves on both
baselines. Relative to standard VPA, Cognitive-EVMM drastically reduces spike response
latency and avoids the large resource slack associated with reactive overprovisioning.
Relative to base EVMM, it achieves faster burst response, lower resource waste, stronger
lower-tail OOM margins, and a higher final scalability-reliability score. The most important
result is not any single number but the consistent pattern across all graphs: the cognitive
controller delivers a better balance among cost efficiency, safety, latency, and operational
continuity.
In summary, Cognitive-EVMM demonstrates that vertical memory autoscaling for state-
ful Kubernetes workloads benefits significantly from situational awareness. By integrating
prediction with confidence, thresholds with context, and actuation with restart-avoidance
priorities, the proposed framework advances beyond both conventional VPA and the
original EVMM baseline and provides a strong systems model for memory-centric elasticity
in modern cloud-native environments.
