\section*{Abstract}

Stateful cloud-native services such as databases, queues, and cache-intensive middle tiers remain difficult to autoscale safely because memory is a hard resource in Kubernetes: under-allocation creates Out-of-Memory (OOM) failures, whereas over-allocation inflates cluster cost and reduces packing efficiency. Standard Vertical Pod Autoscaler (VPA) improves long-horizon right-sizing, but it is primarily recommendation oriented, reactive, and historically tied to disruptive actuation semantics. The Elastic Vertical Memory Management (EVMM) approach of Kang and Yu introduced a proactive memory-centric control loop for Kubernetes-based stateful applications, yet its behavior still depends on uniform trend logic and fixed thresholds that react slowly to abrupt phase changes. This report presents \textbf{Cognitive Elastic Vertical Memory Management (Cognitive-EVMM)}, an improved control framework that augments EVMM with workload-state classification, hybrid forecasting, adaptive thresholds, confidence-aware fallback, and priority-based memory allocation under node pressure.

The proposed system monitors high-frequency memory telemetry from Prometheus, models short-term demand using a hybrid Exponential Moving Average and linear-trend predictor, classifies each control interval as \emph{steady}, \emph{trending}, or \emph{volatile}, and then selects a state-specific scaling policy. A cognitive decision engine combines usage ratio, rate of change, forecast confidence, and memory priority to produce an actuation score for in-place vertical resizing. The design explicitly targets restart avoidance for stateful services and introduces an OOM-guard panic path for near-limit or high-velocity memory bursts. Experimental analysis using the project implementation, synthetic and injected spikes, and comparative plots shows that Cognitive-EVMM reduces spike response latency from 240\,s for standard VPA and 72\,s for base EVMM to 12\,s, improves resource-efficiency score from 62\% to 84\% over the EVMM baseline, and achieves approximately 35\% lower memory waste than the base paper under mixed workloads. The controller also shifts OOM safety margins away from the danger zone while preserving tighter average slack than conventional VPA, yielding a stronger cost-performance-reliability balance for Kubernetes-based stateful applications.

\medskip
\noindent\textbf{Keywords:} Kubernetes; Vertical Pod Autoscaler; EVMM; Stateful Workloads; In-place Pod Resize; Predictive Scaling; Cognitive Control; Memory Elasticity.

\section{Introduction}
\label{sec:introduction}
%% ============================================================

\subsection{Background: Memory Elasticity in Cloud-Native Platforms}

Kubernetes has become the dominant orchestration substrate for microservices because it unifies deployment, service discovery, fault recovery, and scale control in a declarative control plane. Most production clusters already rely on Horizontal Pod Autoscaler (HPA) for throughput scaling and cluster-level autoscalers for node elasticity. However, memory-heavy stateful services do not benefit from horizontal scaling as directly as stateless request handlers. Replicating a front-end worker can absorb traffic; replicating a stateful database replica or stream-processing shard often requires data movement, consistency coordination, cache rewarming, and storage-aware placement. Consequently, many real-world workloads remain bottlenecked by \emph{vertical} resource adequacy rather than pod-count elasticity.

For memory in particular, the operational stakes are high. CPU overuse usually leads to throttling; memory overuse leads to kernel reclamation, cgroup pressure, latency amplification, and eventually OOM termination. These effects are especially harmful for stateful workloads whose working sets are expensive to reconstruct. A vertical memory controller must therefore satisfy two objectives that are naturally in tension: it must maintain sufficient headroom to protect the working set, yet it must avoid persistent slack that wastes node memory and reduces bin-packing density.

\subsection{Horizontal Scaling versus Vertical Scaling}

The distinction between horizontal and vertical autoscaling is central to the motivation of this work.
\begin{itemize}
    \item \textbf{Horizontal scaling} increases or decreases the number of pod replicas. It is effective for embarrassingly parallel request processing, but it is less suitable for monolithic state shards, primary databases, in-memory caches, and single-threaded state coordinators.
    \item \textbf{Vertical scaling} changes per-pod CPU and memory allocations. It is the natural strategy when the application cannot be split quickly, when state transfer is expensive, or when a single pod must preserve session affinity and warm memory state.
\end{itemize}

In practice, stateful services often require both. Yet when memory demand rises abruptly, vertical scaling is usually the first line of defense because it can increase the survivability of the running process without re-partitioning the application. The challenge is that vertical scaling has historically been slower and more disruptive than horizontal scaling in Kubernetes, especially when resource updates require pod eviction or recreation.

\subsection{Limitations of Standard VPA}

The upstream Kubernetes Vertical Pod Autoscaler improves rightsizing by recommending or applying CPU and memory request changes based on observed historical usage \cite{vpa-repo}. Its design is valuable for long-horizon efficiency improvement, but several limitations remain critical for stateful memory management:
\begin{enumerate}[label=\arabic*)]
    \item \textbf{Reactive behavior.} VPA is oriented around accumulated observation windows and recommender outputs, not short-horizon burst anticipation.
    \item \textbf{Weak workload awareness.} The same general policy is applied regardless of whether the workload is stable, trending, or highly volatile.
    \item \textbf{Operational disruption.} Although modern Kubernetes now supports in-place resize capabilities \cite{k8s-resize,k8s-resize-blog}, restart-free behavior is not universally guaranteed for every resize case, and conventional VPA workflows historically depended on pod eviction or recreation.
    \item \textbf{No memory-priority arbitration.} VPA does not reason explicitly about which pods should receive scarce memory first under node pressure.
\end{enumerate}

These characteristics make standard VPA useful for baseline rightsizing, but insufficient for aggressive stateful memory elasticity where burst survivability and sub-minute response are required.

\subsection{Motivation for Cognitive EVMM}

The EVMM baseline by Kang and Yu addressed an important gap by treating vertical memory scaling as a proactive control problem for stateful Kubernetes applications \cite{evmm2025}. It introduced elastic scaling logic that follows observed demand more closely than static VPA policies and explicitly targets stateful behavior. However, the baseline still exhibits two structural limitations in bursty environments. First, a single predictive regime is applied to all workload phases, even though steady nightly traffic, monotonic ramp-up, and instantaneous spikes require different controller gains. Second, fixed decision thresholds create either lag or oscillation when cluster conditions and workload volatility change simultaneously.

The core motivation of Cognitive-EVMM is therefore to make the control loop \emph{context aware}. Instead of asking only ``How much memory was recently consumed?'', the proposed system also asks:
\begin{itemize}
    \item Is the workload currently steady, trending, or volatile?
    \item How confident is the short-term forecast?
    \item How much node pressure exists, and which pod should receive memory first?
    \item Should the controller optimize primarily for efficiency, anticipation, or safety in the current interval?
\end{itemize}

\subsection{Research Problem and Objectives}

This report addresses the following research problem:
\begin{quote}
\emph{How can Kubernetes-based stateful applications be vertically memory-scaled in a proactive, low-waste, restart-avoiding, and OOM-safe manner under mixed workload dynamics?}
\end{quote}

To answer this problem, the report pursues four objectives:
\begin{enumerate}[label=\arabic*)]
    \item design a cognitive extension of EVMM that detects workload phase changes in real time;
    \item formulate a mathematically grounded scaling policy with adaptive thresholds and memory-priority awareness;
    \item implement the control loop in a Kubernetes and Prometheus based prototype;
    \item evaluate the design against standard VPA and the base EVMM approach using latency, waste, safety, and reliability metrics.
\end{enumerate}

\subsection{Key Contributions}

The main contributions of this report are summarized below.
\begin{itemize}
    \item \textbf{Cognitive control extension.} A state-aware controller is proposed to distinguish steady, trending, and volatile workload phases and to change scaling weights accordingly.
    \item \textbf{Hybrid prediction model.} The work combines exponential smoothing with short-term trend inference so that the controller remains stable during smooth periods and still reacts early during ramp-up.
    \item \textbf{Adaptive thresholding.} Scale-up and scale-down thresholds are adjusted online using variance, forecast confidence, and node pressure rather than remaining fixed.
    \item \textbf{Priority-based memory allocation.} A normalized priority score is introduced to arbitrate memory allocation under contention using memory intensity, CPU support, usage variance, and node pressure.
    \item \textbf{Restart-avoidance oriented actuation.} The controller is designed around in-place vertical resizing semantics and therefore targets continuity for stateful services whenever the platform allows it.
    \item \textbf{Comprehensive comparative evaluation.} The report provides graph-by-graph analysis of memory scaling fidelity, resource slack, OOM margin distribution, latency, cost savings, and a final scalability-reliability score.
\end{itemize}

\section{Related Work}
\label{sec:related}
%% ============================================================

\subsection{Kubernetes Vertical Pod Autoscaler}

The Kubernetes autoscaling ecosystem includes HPA, Cluster Autoscaler, and VPA. VPA focuses on right-sizing pod CPU and memory requests over time and is implemented through recommender, updater, and admission components in the Kubernetes autoscaler project \cite{vpa-repo}. Its principal strength lies in improving chronic over- or under-requesting. However, VPA does not fundamentally solve the control-theoretic problem of short-horizon memory surges in stateful services. From a research perspective, VPA is a valuable systems baseline rather than a complete solution for rapid vertical memory elasticity.

\subsection{ElasticDocker}

ElasticDocker pioneered autonomic vertical elasticity for containerized applications by adjusting CPU and memory allocations online based on threshold crossings \cite{elasticdocker}. Its contributions were important because they demonstrated that containers can be vertically adjusted with less disruption than virtual machine era scaling methods. Nonetheless, ElasticDocker predates contemporary Kubernetes-native in-place resize capabilities, does not focus specifically on stateful microservices in Kubernetes, and relies primarily on threshold-triggered behavior rather than adaptive cognitive control.

\subsection{RUBAS and Non-Disruptive Vertical Autoscaling}

Rattihalli \emph{et al.} investigated non-disruptive vertical autoscaling and resource estimation in Kubernetes \cite{rattihalli2019}. Their work is valuable because it highlighted the feasibility of modifying resource allocations without always recreating the pod and quantified estimation challenges in real clusters. In that sense, it forms an important bridge between static rightsizing and truly dynamic vertical control. Yet its emphasis is on feasibility and estimation rather than on memory-specific cognitive decision-making, state classification, or cost-reliability tradeoff optimization.

\subsection{HyScale and Hybrid Autoscaling}

HyScale combined horizontal scaling, vertical scaling, and network-level reasoning for Dockerized microservices in cloud data centers \cite{hyscale}. The paper demonstrated that purely horizontal or purely vertical scaling is often suboptimal when service chains and network bottlenecks are involved. This insight remains relevant here: stateful systems also require coordinated reasoning across multiple resource dimensions. However, HyScale primarily targets service-level scaling orchestration rather than fine-grained memory control for a single stateful pod's working set.

\subsection{EVMM Baseline by Kang and Yu}

The closest antecedent to this work is EVMM, which targets elastic vertical memory management for container-based stateful applications in Kubernetes \cite{evmm2025}. EVMM recognizes that memory is both performance critical and failure sensitive in stateful services. Its baseline contribution is to move beyond static VPA-style resizing and to use shorter telemetry intervals together with proactive logic for memory adjustment. The base implementation in this project captures that philosophy through a memory-priority score, trend-aware scale-up logic, and reclaim policy under low utilization.

Despite its relevance, the baseline reveals several limitations under mixed dynamics:
\begin{itemize}
    \item the same general scaling logic is reused across smooth ramps and abrupt spikes;
    \item decision thresholds are largely fixed;
    \item prediction confidence is not explicitly used to attenuate risky forecasts;
    \item emergency handling remains less sensitive to sudden rate-of-change surges than desired for strict OOM protection.
\end{itemize}

\subsection{Research Gaps}

The literature synthesis reveals four research gaps that motivate Cognitive-EVMM.
\begin{enumerate}[label=\arabic*)]
    \item \textbf{Phase-unaware decision loops.} Existing methods usually treat recent telemetry as a homogeneous signal and do not separate stable, trending, and volatile workload phases.
    \item \textbf{Insufficient memory-specific urgency modeling.} Many systems optimize generic resource usage but do not explicitly prioritize memory survivability for stateful pods.
    \item \textbf{Weak coupling between prediction and confidence.} Forecasts are often used directly even when their statistical reliability is poor.
    \item \textbf{Limited contention-aware allocation.} Cluster-level pressure is often ignored during per-pod vertical decision-making.
\end{enumerate}

\section{System Architecture}
\label{sec:architecture}
%% ============================================================

\subsection{Architectural Overview}

Cognitive-EVMM is organized as a closed-loop control pipeline deployed alongside Kubernetes workloads. The architecture follows the monitor-analyze-decide-act pattern but introduces a cognitive layer between prediction and actuation. The full pipeline consists of four core modules:
\begin{enumerate}[label=\arabic*)]
    \item \textbf{Monitoring module}
    \item \textbf{Prediction engine}
    \item \textbf{Cognitive decision engine}
    \item \textbf{Scaling controller}
\end{enumerate}

At a high level, Prometheus collects memory telemetry from the target pod, the monitoring module maintains a bounded history window, the prediction engine estimates near-future demand, the cognitive engine classifies workload state and computes a scaling score, and the controller applies an in-place resource patch subject to safety constraints and cooldown rules.

\subsection{Monitoring Module}

The implementation queries \keyword{container\_memory\_working\_set\_bytes} from Prometheus every 10\,s, converts the metric to MiB, and appends it to a rolling history. The history length in the implementation is capped at 60 samples, which corresponds to approximately 10 minutes of recent context. In addition to raw memory usage, the controller derives:
\begin{itemize}
    \item utilization ratio $u_i(t) = U_i(t)/L_i(t)$,
    \item instantaneous rate of change $r_i(t)$,
    \item short-window variance and volatility indicators,
    \item current memory limit from the Kubernetes deployment spec.
\end{itemize}

The monitoring module therefore serves two roles: it produces operational telemetry for scaling decisions, and it exposes research metrics such as current score, workload class, forecast confidence, savings in MB-hours, and panic count via Prometheus-compatible gauges.

\subsection{Prediction Engine}

The prediction engine estimates near-future memory demand over a short horizon $H$. The implementation uses a hybrid approach:
\begin{enumerate}[label=\arabic*)]
    \item an Exponential Moving Average (EMA) captures short-term smoothed behavior and filters high-frequency noise;
    \item a linear regression model over the recent history estimates the trend slope and $R^2$ confidence;
    \item both signals are combined to form a hybrid demand forecast.
\end{enumerate}

This design is intentionally lightweight. It avoids the runtime overhead and training requirements of heavy machine learning models while still encoding two important intuitions: recent usage should matter more than older usage, and persistent ramps should influence proactive limit changes before threshold breach occurs.

\subsection{Cognitive Decision Engine}

The cognitive engine is the central innovation of the proposed architecture. It first classifies the workload into one of three behavioral states:
\begin{itemize}
    \item \textbf{Steady}: low variance, weak directional trend, low rate fluctuation.
    \item \textbf{Trending}: strong linear direction with sufficiently high forecast confidence.
    \item \textbf{Volatile}: bursty or rapidly changing usage with high rate variance or danger-zone urgency.
\end{itemize}

After classification, the engine selects a weighting vector for decision features. In steady mode, direct utilization dominates because efficiency is the primary objective. In trending mode, forecasted demand receives larger weight to anticipate continued ramp-up. In volatile mode, rate-of-change and safety take precedence so that the controller reacts before OOM conditions develop.

The implementation also includes confidence-aware fallback: when forecast confidence falls, trend weight is attenuated and direct usage receives more weight. This prevents unstable actuation when linear fit quality deteriorates during abrupt behavioral transitions.

\subsection{Scaling Controller}

The scaling controller is the actuation layer that patches Kubernetes resource limits and requests. In the prototype, the controller updates the target deployment through the Kubernetes API and respects four guardrails:
\begin{enumerate}[label=\arabic*)]
    \item \textbf{minimum and maximum memory bounds} (128\,MiB to 4096\,MiB);
    \item \textbf{cooldown control} (90\,s) to limit oscillation;
    \item \textbf{panic scaling} when near-limit danger is detected;
    \item \textbf{conservative scale-down} to avoid repeated shrinking and re-expanding.
\end{enumerate}

The sample workload manifest explicitly enables memory \keyword{resizePolicy} with \keyword{restartPolicy: NotRequired}, making the configuration compatible with restart-avoiding vertical adjustments where supported by the cluster version and runtime implementation. In production terms, this is critical: upward resizing is prioritized because it directly protects the process working set, while downscaling is intentionally more conservative because some memory decrease cases may still be operationally constrained even with modern in-place resize support.

\subsection{End-to-End Workflow}

The end-to-end workflow for one control interval is summarized below.
\begin{enumerate}[label=\arabic*)]
    \item Prometheus samples the target pod every 10\,s.
    \item The monitoring module fetches memory usage and updates the history window.
    \item The predictor computes EMA, trend slope, and forecast confidence.
    \item The classifier labels the interval as steady, trending, or volatile.
    \item The decision engine computes a cognitive score and evaluates OOM-guard conditions.
    \item The scaling controller computes the new limit and patches Kubernetes resources if cooldown and bound checks pass.
    \item Exported metrics record the actuation outcome for visualization and research analysis.
\end{enumerate}

\section{Proposed Methodology}
\label{sec:methodology}
%% ============================================================

\subsection{Problem Formulation}

Consider a node or cluster segment hosting $N$ stateful pods. Let $U_i(t)$ denote the observed memory usage of pod $i$ at control instant $t$, and let $L_i(t)$ denote its configured memory limit. The control objective is to choose $L_i(t+\Delta)$ such that memory waste is minimized while OOM risk, scaling latency, and disruptive actuation are constrained.

We formulate the optimization target as
\begin{equation}
\label{eq:objective}
\min_{\{L_i\}} J(t) = \lambda_1 \sum_{i=1}^{N} [L_i(t)-U_i(t)]^{+}
+ \lambda_2 \sum_{i=1}^{N} \mathcal{R}^{\text{oom}}_i(t)
+ \lambda_3 \sum_{i=1}^{N} \mathcal{T}^{\text{scale}}_i(t)
+ \lambda_4 \sum_{i=1}^{N} \mathcal{C}^{\text{restart}}_i(t),
\end{equation}
subject to
\begin{equation}
\label{eq:constraint1}
\sum_{i=1}^{N} L_i(t) \leq M^{\text{avail}}_{\text{node}}(t),
\end{equation}
\begin{equation}
\label{eq:constraint2}
L_i^{\min} \leq L_i(t) \leq L_i^{\max}.
\end{equation}

Here, $[x]^+ = \max(x,0)$ measures positive slack, $\mathcal{R}^{\text{oom}}_i(t)$ is a risk proxy linked to low safety margin, $\mathcal{T}^{\text{scale}}_i(t)$ models actuation delay, and $\mathcal{C}^{\text{restart}}_i(t)$ captures the operational penalty of restart-inducing resizes. The coefficients $\lambda_1,\dots,\lambda_4$ encode system preference. For stateful services, $\lambda_2$ and $\lambda_4$ are typically higher than in stateless deployments.

\subsection{Priority Scoring Model}

To arbitrate memory allocation under shared node pressure, Cognitive-EVMM assigns each pod a normalized priority score:
\begin{equation}
\label{eq:priority}
P_i(t) = \alpha \hat{m}_i(t) + \beta \hat{c}_i(t) + \gamma \hat{\sigma}_i(t) + \delta \hat{\rho}_n(t) + \eta \omega_i,
\end{equation}
where
\begin{itemize}
    \item $\hat{m}_i(t)$ is normalized memory pressure, typically $U_i(t)/L_i(t)$;
    \item $\hat{c}_i(t)$ is normalized CPU usage or support demand;
    \item $\hat{\sigma}_i(t)$ is normalized short-window memory variance;
    \item $\hat{\rho}_n(t)$ is node pressure, such as used memory over allocatable node memory;
    \item $\omega_i$ is a service criticality factor for business or statefulness priority.
\end{itemize}

The weights satisfy $\alpha+\beta+\gamma+\delta+\eta=1$. In the single-deployment prototype, $\omega_i$ can be treated as constant, but the formulation generalizes naturally to multi-tenant clusters. Compared with base EVMM, the proposed score explicitly links pod-level urgency to node-level pressure, which becomes important when multiple stateful pods compete for limited memory.

\subsection{Predictive Scaling Mechanism}

The forecast for memory demand over horizon $H$ is defined as a convex combination of a smoothed signal and a trend signal:
\begin{equation}
\label{eq:ema}
\text{EMA}_i(t) = \lambda U_i(t) + (1-\lambda)\text{EMA}_i(t-\Delta),
\end{equation}
\begin{equation}
\label{eq:trend}
\text{Trend}_i(t+H) = U_i(t) + H \cdot \dot{U}_i(t),
\end{equation}
\begin{equation}
\label{eq:hybrid}
\hat{U}_i(t+H) = \kappa \text{EMA}_i(t) + (1-\kappa)\text{Trend}_i(t+H),
\end{equation}
where $\dot{U}_i(t)$ is the estimated slope from linear regression and $\kappa \in [0,1]$ balances stability against anticipation. In the prototype, regression confidence is captured through $R^2$:
\begin{equation}
\label{eq:confidence}
\chi_i(t) = \max(0, R_i^2(t)).
\end{equation}

Confidence then modulates how aggressively the trend component is trusted. If $\chi_i(t)$ is low, the controller falls back toward direct usage and EMA-dominant behavior. This is preferable to blindly following a low-quality forecast.

\subsection{Adaptive Threshold Logic}

Fixed thresholds are easy to implement but perform poorly across heterogeneous traffic phases. Cognitive-EVMM therefore defines adaptive scale-up and scale-down thresholds:
\begin{equation}
\label{eq:theta_up}
\theta_i^{\uparrow}(t) = \theta_0^{\uparrow} - a_1 \hat{\sigma}_i(t) - a_2 \hat{\rho}_n(t) - a_3 [1-\chi_i(t)],
\end{equation}
\begin{equation}
\label{eq:theta_down}
\theta_i^{\downarrow}(t) = \theta_0^{\downarrow} - b_1 [1-\chi_i(t)] + b_2 [1-\hat{\rho}_n(t)].
\end{equation}

Equation~(\ref{eq:theta_up}) lowers the scale-up threshold when variance is high, node pressure is high, or confidence in the current model is low. This means the controller becomes more conservative about safety during uncertain or bursty periods. Equation~(\ref{eq:theta_down}) ensures that downscaling is delayed when forecast confidence is low or when node pressure does not justify aggressive reclamation.

\subsection{Cognitive Workload Classification}

The classifier uses recent telemetry to map each interval into one of three workload states:
\begin{equation}
\label{eq:class_steady}
\mathcal{S}_i(t)=
\begin{cases}
\text{steady}, & \hat{\sigma}_i(t) < \tau_{\sigma} \land R_i^2(t) < \tau_r \\
\text{trending}, & R_i^2(t) \geq \tau_r \land \dot{U}_i(t) > 0 \\
\text{volatile}, & \text{otherwise or } |r_i(t)| > \tau_{\text{roc}}.
\end{cases}
\end{equation}

This classification is intentionally simple enough for fast control-loop execution while remaining semantically expressive. The logic aligns with the implementation: steady workloads prioritize tight resource tracking, trending workloads prioritize forecasted headroom, and volatile workloads prioritize near-term survivability.

\subsection{Cognitive Decision Function}

For a workload state $k \in \{\text{steady},\text{trending},\text{volatile}\}$, let the state-specific weight vector be
\begin{equation}
\mathbf{w}^{(k)} = [w_u^{(k)}, w_r^{(k)}, w_f^{(k)}, w_p^{(k)}].
\end{equation}
The cognitive decision score is then
\begin{equation}
\label{eq:decision}
D_i(t) = w_u^{(k)} u_i(t) + w_r^{(k)} \tilde{r}_i(t) + w_f^{(k)} \chi_i(t)\frac{\hat{U}_i(t+H)}{L_i(t)} + w_p^{(k)} P_i(t),
\end{equation}
where $\tilde{r}_i(t)$ is the normalized rate of change. In the concrete prototype, the weighting pattern follows:
\begin{itemize}
    \item steady: usage-dominant;
    \item trending: forecast-dominant;
    \item volatile: ROC-dominant.
\end{itemize}

The output score $D_i(t)$ is mapped to a bounded scale factor:
\begin{equation}
\label{eq:scalefactor}
s_i(t)=
\begin{cases}
1.5, & D_i(t) > \tau_{85} \\
1.2, & \tau_{70} < D_i(t) \leq \tau_{85} \\
0.8, & \tau_{25} \leq D_i(t) < \tau_{40} \\
0.6, & D_i(t) < \tau_{25} \\
1.0, & \text{otherwise.}
\end{cases}
\end{equation}

The new target limit becomes
\begin{equation}
\label{eq:newlimit}
L_i'(t) = \text{clip}(s_i(t)L_i(t),L_i^{\min},L_i^{\max}).
\end{equation}

\subsection{OOM-Guard and Panic Scaling}

The controller includes an emergency branch for situations where standard score-based resizing may be too slow. If the pod enters the danger zone, defined by
\begin{equation}
\label{eq:panic}
\frac{U_i(t)}{L_i(t)} > 0.92
\quad \text{or} \quad
|r_i(t)| > \tau_{\text{panic}},
\end{equation}
the controller bypasses the normal scoring path and applies a panic multiplier:
\begin{equation}
\label{eq:paniclimit}
L_i^{\text{panic}}(t) = \text{clip}(2.0L_i(t),L_i^{\min},L_i^{\max}).
\end{equation}

In the repository implementation, near-limit panic is explicit and ROC strongly influences state selection and score; in the plot-based experimental model, the burst path additionally uses an immediate ROC override to emulate aggressive high-velocity reaction. Both interpretations are consistent with the design goal: preventing OOM rather than merely reacting after breach.

\subsection{Algorithmic Summary}

\begin{lstlisting}[caption={Pseudo-code for the proposed Cognitive-EVMM controller.},label={lst:cognitive_evmm}]
Input:
  telemetry stream, memory bounds, cooldown, prediction horizon H
Output:
  new memory request/limit for target pod

while controller is active do
    U_t <- fetch current memory usage from Prometheus
    L_t <- fetch current memory limit from Kubernetes
    History <- append(U_t) and trim to rolling window

    r_t <- rate_of_change(History)
    sigma_t <- variance(History)
    rho_t <- node_pressure()
    P_t <- priority_score(U_t, CPU_t, sigma_t, rho_t, criticality)

    EMA_t <- exponential_average(History)
    Trend_t, conf_t <- linear_forecast(History, H)
    U_hat <- hybrid_forecast(EMA_t, Trend_t)

    State <- classify(sigma_t, r_t, conf_t, Trend_t)

    if danger_zone(U_t, L_t, r_t) then
        L_new <- clip(2.0 * L_t, L_min, L_max)
    else
        Weights <- select_state_weights(State)
        D_t <- weighted_score(U_t/L_t, normalize(r_t),
                              conf_t * U_hat/L_t, P_t, Weights)
        Thresholds <- adapt_thresholds(sigma_t, rho_t, conf_t)
        Scale <- map_score_to_step(D_t, Thresholds)
        L_new <- clip(Scale * L_t, L_min, L_max)
    end if

    if cooldown_elapsed() and L_new != L_t then
        patch_kubernetes_resources(L_new)
        export_observability_metrics()
    end if

    sleep(10 seconds)
end while
\end{lstlisting}

\subsection{Why the Method Improves on VPA and EVMM}

The methodology improves on standard VPA because it is \emph{phase aware}, \emph{short-horizon predictive}, and \emph{memory-priority conscious}. It improves on the base EVMM design because it couples prediction with confidence, couples scale thresholds with current variance and node pressure, and separates controller behavior across workload phases instead of using a single trend-centric regime. Conceptually, Cognitive-EVMM is not just ``more aggressive EVMM''; it is a different control strategy in which the controller first decides \emph{what kind of memory dynamics} it is observing and then chooses the appropriate scaling law.

\section{Experimental Setup}

\subsection{Cluster Environment}

The experimental prototype is implemented as a Kubernetes-deployed Python autoscaler using the official Kubernetes Python client, Prometheus API client, Pandas-based feature processing, and scikit-learn linear regression. The autoscaler is packaged as a deployment with RBAC permissions to read and patch deployments in the cluster. The target workload is a sample stateful-like containerized application deployed with explicit memory requests and limits, and with memory resize policy configured to avoid restarts where supported by the cluster runtime.

The experimental environment includes the following practical components:
\begin{itemize}
    \item Kubernetes deployment for the autoscaler controller;
    \item Prometheus for metric collection;
    \item sample workload deployment with resizable memory limits;
    \item Grafana dashboards and exported controller metrics for observation;
    \item workload generators for steady, trending, and burst phases.
\end{itemize}

\subsection{Target Workloads}

Two workload-generation paths are used in the project artifacts.
\begin{enumerate}[label=\arabic*)]
    \item \textbf{Synthetic trace generation.} The plot generator combines sinusoidal baseline demand, random noise, a large sudden spike, and a sustained upward trend. This produces a mixed workload containing all three controller states in a single experiment.
    \item \textbf{Live spike injection.} The spike trigger script allocates a large memory object inside the sample application pod and holds it for a fixed period, creating a sharp burst suitable for latency and OOM-guard evaluation.
\end{enumerate}

The mixed traces are intentionally useful for research because they expose three distinct controller stress cases:
\begin{itemize}
    \item \textbf{steady periods} test whether the controller can reclaim slack instead of holding conservative limits;
    \item \textbf{trend periods} test whether predictive scaling can widen headroom before threshold breach;
    \item \textbf{burst periods} test whether the safety logic acts quickly enough to avoid OOM.
\end{itemize}

\subsection{Compared Baselines}

Three systems are compared throughout the report.
\begin{enumerate}[label=\arabic*)]
    \item \textbf{Standard VPA.} A reactive baseline with relatively delayed response and historically disruptive actuation semantics.
    \item \textbf{Base EVMM.} The implementation derived from the 2025 EVMM paper, using priority scoring and predictive adjustment without cognitive phase switching.
    \item \textbf{Proposed Cognitive-EVMM.} The improved controller with hybrid prediction, adaptive thresholds, workload classification, and OOM-guard logic.
\end{enumerate}

The comparison is therefore deliberately incremental: VPA provides the common Kubernetes baseline, EVMM provides the relevant state-of-the-art research baseline, and Cognitive-EVMM isolates the gains produced by the proposed extensions.

\subsection{Evaluation Metrics}

The evaluation uses the following metrics.

\subsubsection{Memory Scaling Efficiency}

Scaling efficiency measures how closely the allocated limit follows actual memory demand without entering unsafe territory. Let slack be
\begin{equation}
\label{eq:slack}
S_i(t)=L_i(t)-U_i(t).
\end{equation}
Low positive slack is desirable; negative slack indicates a demand overshoot and thus heightened OOM risk.

\subsubsection{Resource Waste}

Cumulative memory waste over experiment horizon $T$ is
\begin{equation}
\label{eq:waste}
W_i = \int_0^T [L_i(t)-U_i(t)]^{+}dt.
\end{equation}
This metric captures the economic cost of conservative sizing. The implementation also exports saved MB-hours relative to a maximum limit.

\subsubsection{OOM Safety Margin}

The instantaneous OOM margin is
\begin{equation}
\label{eq:margin}
M_i(t)=L_i(t)-U_i(t).
\end{equation}
The distribution of $M_i(t)$ indicates whether the controller spends too much time in the danger zone. A system may be efficient on average while still unsafe if lower-tail margins collapse during bursts.

\subsubsection{Scaling Latency}

Scaling latency is the elapsed time between a meaningful workload demand transition and the controller establishing sufficient new headroom. In the comparative plots, the reference event is a sudden 900\,MiB spike. Lower latency directly improves survivability for stateful services.

\subsubsection{Cost Savings Rate}

Cost savings are evaluated as a normalized relative reduction in consumed memory-hours:
\begin{equation}
\label{eq:cost}
\text{CSR} = \frac{C_{\text{baseline}} - C_{\text{method}}}{C_{\text{baseline}}}.
\end{equation}
Although the report uses memory-centric workloads rather than cloud-provider billing traces, CSR is still a meaningful proxy because memory reservations are a primary driver of node count and instance sizing.

\subsubsection{Final Evaluation Score}

To summarize multi-objective behavior, a report-level balanced efficiency index (BEI) is defined as
\begin{equation}
\label{eq:bei}
\text{BEI} = 0.30E + 0.25S + 0.25R + 0.20Q,
\end{equation}
where $E$ is normalized efficiency, $S$ is normalized safety, $R$ is responsiveness, and $Q$ is stability/reliability. This score is not used by the controller at runtime; it is used only for comparative research synthesis.

\subsection{Threat Model and Assumptions}

The experimental design assumes that Prometheus telemetry reflects application memory pressure with sufficiently low lag, that the Kubernetes cluster supports practical in-place memory resize behavior for the chosen workload pattern, and that the target deployment is a valid proxy for a stateful service whose restart cost is materially higher than that of a stateless worker. The experiments therefore emphasize \emph{controller behavior} and \emph{comparative actuation quality}. They do not attempt to model every possible storage engine or scheduler implementation detail.

\subsection{Memory Scaling Comparison}

Figure~\ref{fig:comparison_trace} compares the memory limit traces of standard VPA, base EVMM, and Cognitive-EVMM against workload demand. The differences are architecturally revealing.

\begin{figure}[t]

Standard VPA shows a pronounced stair-step pattern. Limits move upward slowly, remain high for longer than necessary, and only reclaim memory after substantial delay. This behavior is unsurprising for a reactive system: it is designed to avoid oscillation, not to track short-lived memory transients tightly. The result is a large safety envelope, but one paid for through persistent slack.

Base EVMM tracks the workload more closely. The trace validates the usefulness of short-window predictive logic: compared with VPA, the controller rises earlier and reclaims more memory after peaks. However, during the large spike and the later upward ramp, the base EVMM curve still approaches the demand line too closely. This reflects the limitation of using a mostly uniform predictive law for heterogeneous phases. Trend information helps during ramps, yet it underreacts when the workload changes more quickly than the fitted trend can extrapolate.

Cognitive-EVMM produces the most desirable shape. During calm periods, it collapses the gap between limit and usage, indicating efficient reclamation. During the ramp and burst windows, it expands quickly and earlier than the base EVMM curve. The result is neither the wide slack of VPA nor the thin lower-tail margin of base EVMM, but a context-dependent envelope that expands and contracts according to workload state.

\section{Discussion}

\subsection{Strengths of the Proposed System}

The strongest property of Cognitive-EVMM is that it improves the multi-objective balance of vertical memory control. Stateful applications care about continuity, not only average utilization. The proposed system acknowledges this by elevating restart avoidance and lower-tail memory safety to first-class design goals. At the same time, it does not abandon efficiency; it simply stops treating every interval as if it were equally dangerous.

Three strengths stand out.
\begin{enumerate}[label=\arabic*)]
    \item \textbf{Fast safety response.} The controller reacts to high-risk intervals before a hard limit breach occurs.
    \item \textbf{Efficient calm-period behavior.} Resource reclamation is more decisive during steady phases, reducing cluster-wide memory waste.
    \item \textbf{Explainable logic.} The cognitive layer uses interpretable features such as variance, ROC, confidence, and node pressure. This is operationally attractive because SRE teams can reason about why a scaling decision occurred.
\end{enumerate}

\subsection{Trade-offs and Operational Considerations}

No autoscaler is free of trade-offs. The proposed method makes several explicit design choices.

First, panic scaling intentionally over-allocates memory for short periods to avoid catastrophic under-allocation. This can temporarily increase slack. However, the evaluation indicates that the total waste remains lower than that of both baselines because the controller returns to tight operation quickly after the event.

Second, adaptive thresholds and state classification require frequent, reliable telemetry. If metric freshness degrades, the controller may act on stale observations. This risk is mitigated partly by confidence-aware fallback, but robust observability remains a prerequisite for deployment.

Third, downscaling is intentionally conservative. This is not a weakness but a deliberate safety decision. In-place upward resizing is usually the highest-value action for stateful processes; aggressive downward resizing can reintroduce the very instability the system is designed to avoid.

\subsection{Real-World Applicability}

The proposed system is especially relevant for the following categories of workloads:
\begin{itemize}
    \item primary or leader replicas of databases;
    \item message brokers and queue consumers with bursty memory buffering;
    \item stream processors with state stores;
    \item in-memory caches and session services;
    \item batch and analytics jobs with phase-changing memory footprints.
\end{itemize}

In such systems, avoiding a restart is often more valuable than preserving a perfectly minimal memory reservation at every moment. Cognitive-EVMM supports this operational reality by scaling vertically in a way that preserves service continuity whenever the underlying platform permits in-place updates.

\subsection{Validity Considerations}

Several validity considerations should be stated explicitly.
\begin{itemize}
    \item \textbf{Workload representativeness.} The project uses synthetic mixed traces and injected spikes, which are appropriate for controller stress testing but do not capture every application-specific memory pathology.
    \item \textbf{Platform semantics.} In-place resizing behavior depends on Kubernetes version, runtime support, and resize direction. The report therefore frames the system as restart-avoidance oriented rather than making an unconditional no-restart guarantee for every resize case.
    \item \textbf{Prototype scope.} The current implementation targets one deployment at a time. The priority formulation is nevertheless useful because it defines how the same logic should extend to multi-pod memory contention.
\end{itemize}

These caveats do not weaken the main contribution. Instead, they clarify the precise scope in which the presented results should be interpreted: as a robust comparative study of a cognitive improvement to EVMM for Kubernetes-based stateful memory management.

\subsection{Implications for Kubernetes Resource Management}

The broader implication of this work is that vertical memory management in Kubernetes should not be viewed as a narrow recommendation problem. It is a control problem with workload semantics, uncertainty, and failure asymmetry. Memory under-allocation is far more dangerous than memory over-allocation for stateful applications, yet indiscriminate safety margins are economically unsustainable. The results indicate that the right solution is not a single universal threshold or a heavier forecasting model in isolation, but a controller that adapts its own reasoning mode to the current operating regime.

%% ============================================================
\section{Conclusion}
\label{sec:conclusion}
%% ============================================================

This report presented Cognitive-EVMM, an improved vertical memory management framework for Kubernetes-based stateful applications. The work began from a practical gap in cloud-native autoscaling: standard VPA is useful for long-horizon rightsizing but reacts too slowly and too generically for burst-prone stateful workloads, while the 2025 EVMM baseline, though substantially better, still applies a largely uniform predictive logic across heterogeneous workload phases.

The proposed system addresses this gap through five tightly coupled design elements: high-frequency monitoring, hybrid short-horizon forecasting, cognitive workload classification, adaptive thresholding, and priority-based memory allocation. The resulting controller shifts policy emphasis according to observed workload state, using efficiency-biased behavior during steady periods, prediction-biased behavior during trending periods, and safety-biased behavior during volatile periods. This is the central technical contribution of the report.

The comparative evaluation shows that the proposed design materially improves on both baselines. Relative to standard VPA, Cognitive-EVMM drastically reduces spike response latency and avoids the large resource slack associated with reactive overprovisioning. Relative to base EVMM, it achieves faster burst response, lower resource waste, stronger lower-tail OOM margins, and a higher final scalability-reliability score. The most important result is not any single number but the consistent pattern across all graphs: the cognitive controller delivers a better balance among cost efficiency, safety, latency, and operational continuity.

In summary, Cognitive-EVMM demonstrates that vertical memory autoscaling for stateful Kubernetes workloads benefits significantly from situational awareness. By integrating prediction with confidence, thresholds with context, and actuation with restart-avoidance priorities, the proposed framework advances beyond both conventional VPA and the original EVMM baseline and provides a strong systems model for memory-centric elasticity in modern cloud-native environments.
